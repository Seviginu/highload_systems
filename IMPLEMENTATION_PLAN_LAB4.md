## 2. Предлагаемый объем

Добавить Kafka из трех брокеров, `notification-service` и `file-service`. Все четыре бизнес-сервиса привести к Clean Architecture. Сохранить действующие API и ограничения ЛР1–3.

| Требование ЛР4 | Предлагаемая реализация |
|---|---|
| Межсервисное взаимодействие через брокер, где возможно | События tracker → notification и file → notification через Kafka |
| Уведомления | Постоянно хранимаемые уведомления пользователя с REST API просмотра и отметки прочтения |
| Минимум 3 брокера, несколько топиков, репликация | 3 Kafka-узла в KRaft, 3 основных топика, replication factor 3 |
| Загрузка и получение файлов | Отдельный file-service с JWT, бинарным хранилищем и метаданными |
| Clean Architecture во всех микросервисах | Независимые domain/application, внешние адаптеры REST, БД, Kafka, Security и конфигурация |

Рабочее допущение: уведомления внутри приложения, доступные через REST, удовлетворяют заданию. Email, Telegram и WebSocket не указаны в требованиях. Это трактовку стоит явно зафиксировать при обсуждении плана с преподавателем; внешняя доставка добавляется только при необходимости.

### Какие взаимодействия оставить синхронными

Сохранить Feign + Circuit Breaker для проверки пользователей перед созданием/изменением проекта, задачи и участника. Сейчас вызывающий код должен сразу знать, существует ли пользователь и является ли он тимлидом. Замена на локальную проекцию из событий изменит гарантии и потребует отдельного решения для начальной загрузки, отставания и удаления пользователей.

Загрузка и скачивание файла, login и чтение API также остаются HTTP. Содержимое файлов через Kafka не передается. Асинхронно выполняются побочные действия, для которых не нужен немедленный ответ: формирование уведомлений.

Такое разделение сохраняет Feign из ЛР2 и демонстрирует осмысленное применение Kafka в ЛР4. Полный отказ от HTTP не требуется формулировкой задания.

## 3. Kafka и контракты

Для учебного Compose использовать три узла с совмещенными ролями broker/controller и quorum из трех контроллеров. У каждого узла отдельный volume и node ID. Это учебная конфигурация на одном компьютере; она проверяет отказ процесса/контейнера, но не отказ физического хоста.

- Создавать топики отдельным идемпотентным init-сервисом после готовности кластера; отключить автоматическое создание.
- Для основных топиков: 3 partitions, replication factor 3, `min.insync.replicas=2`.
- Producer: `acks=all`, idempotence; bootstrap servers содержат все три брокера.
- Настроить replication factor внутренних offset/transaction-топиков, если последние используются; не оставлять внутренние топики с единственной репликой.
- Подобрать и закрепить стабильный Docker image tag при реализации. Spring Kafka брать из dependency management текущего Spring Boot; без отдельного обновления Boot/Cloud.
- Kafka доступна сервисам внутри Compose. Для обычного запуска не требуется открывать брокеры во внешнюю сеть.

| Топик | Producer | События | Consumer и результат |
|---|---|---|---|
| `tracker.task.events.v1` | tracker-service | `TaskAssigned`, `TaskStatusChanged` | notification-service: уведомить исполнителя о назначении, автора — о смене статуса |
| `tracker.project.events.v1` | tracker-service | `ProjectMemberAdded` | notification-service: уведомить добавленного/повторно активированного участника |
| `files.events.v1` | file-service | `FileUploaded` | notification-service: уведомить владельца об успешной загрузке |

Для каждого основного топика создать соответствующий `.dlt` с replication factor 3. Retry сначала делать ограниченным внутри обработки; отдельную сеть retry-топиков для минимальной реализации не вводить.

Общий конверт: `eventId` (UUID), `eventType`, `schemaVersion`, `occurredAt`, `aggregateId`, `aggregateVersion`, `actorId`, `recipientIds`, `payload`. `aggregateVersion` использовать там, где агрегат версионируется. Партиционировать по ID агрегата. В payload передавать только необходимые ID и краткий контекст, без паролей, хэшей, Authorization/JWT и бинарных файлов.

Контракты можно вынести в небольшой Maven-модуль `event-contracts`: только Java-типы транспортных сообщений. Не помещать туда Entity, бизнес-сервисы, KafkaTemplate или общие репозитории. Kafka-адаптеры переводят внутренние события в эти контракты; domain от модуля транспортных контрактов не зависит.

Зафиксировать правила генерации:

- При создании задачи с исполнителем — `TaskAssigned`; при реальной смене исполнителя через update/move — также `TaskAssigned`. При снятии исполнителя уведомлять некого.
- `TaskStatusChanged` создавать при реальной смене статуса как через PATCH, так и через существующий PUT. Сохранение прежнего значения не создает событие.
- Первичное добавление и повторная активация участника создают `ProjectMemberAdded`, включая автоматическое членство тимлида при создании проекта.
- Получателей определять в producer по результату бизнес-операции. Consumer не вызывает user-service для каждой записи.
- При `recipientId == actorId` для задач можно подавлять уведомление; подтверждение загрузки файла и вступление в проект сохранять и для самого инициатора. Правила закрепить тестами.

## 4. Надежность доставки

Использовать небольшой polling outbox в tracker-service и file-service:

1. Изменение агрегата и запись исходящего события выполняются в одной локальной транзакции БД.
2. Publisher читает ожидающие записи и отправляет их в Kafka вне пользовательского HTTP-запроса.
3. Только после подтверждения Kafka помечает запись опубликованной. При ошибке сохраняет попытку и повторяет отправку с задержкой.
4. Падение между отправкой и фиксацией результата может дать дубликат. Гарантия — at-least-once, а не exactly-once между БД и Kafka.
5. Consumer в одной транзакции сохраняет обработанный `eventId` и все уведомления события. Повторное событие не создает новые уведомления; ограничение уникальности также защищает от конкурентной обработки.
6. Offset подтверждается после успешного commit БД. Временные ошибки повторяются, невалидные/неподдерживаемые сообщения после заданного числа попыток уходят в DLT. Если публикация в DLT не удалась, исходное сообщение не считается обработанным.

Для первой реализации достаточно одного publisher на сервис с последовательной отправкой записей одного агрегата; не пропускать более раннюю неотправленную запись этого агрегата. Ключ партиции обеспечивает порядок в Kafka только при корректном порядке публикации. Масштабируемые lease/claim-механизмы и Debezium не входят в обязательный объем.

При недоступной Kafka CRUD продолжает сохранять данные и outbox. После восстановления уведомления доставляются. Readiness HTTP-сервиса не должна блокировать этот режим только из-за Kafka. Предусмотреть ограничение размера batch, диагностику отставания и очистку старых опубликованных записей.

Outbox и дедупликация не названы отдельными пунктами задания, но включены в план для защиты от потери уведомления между commit БД и отправкой в брокер.

## 5. notification-service

Минимальный стек: Spring MVC + Spring Data JPA + PostgreSQL + Spring Kafka. Новым сервисам не обязательно быть реактивными: требования WebFlux/R2DBC и WebFlux/JPA уже обеспечивают существующие сервисы.

Модель уведомления: `id`, `eventId`, `recipientId`, `type`, `message`, `resourceType`, `resourceId`, `createdAt`, `readAt`. Отдельная таблица обработанных событий обеспечивает дедупликацию всего сообщения.

API через Gateway:

- `GET /api/v1/notifications?page=0&size=20` — только свои уведомления, до 50 записей, `X-Total-Count`; стабильная сортировка по времени и ID.
- `PATCH /api/v1/notifications/{id}/read` — идемпотентная отметка своего уведомления прочитанным, 204.

`recipientId` берется из проверенного JWT для запросов, а не из query/body. Доступ к чужому уведомлению закрыт, в том числе ADMIN: отдельного административного просмотра план не вводит. Уведомление считается доставленным в этом варианте после сохранения в БД, прочитанным — только после PATCH.

У сервиса собственная БД и Liquibase. Зарегистрировать в Eureka, подключить Config Server, `security-common`, общий Swagger и Docker build.

## 6. file-service

Минимальный стек: Spring MVC + Spring Data JPA + PostgreSQL. Для ограниченного учебного объема хранить бинарные данные в PostgreSQL `bytea`: это позволяет атомарно сохранить файл, метаданные и outbox без согласования файловой системы и БД. Лимит одного файла — настраиваемый, по умолчанию 10 MiB. У БД собственный постоянный Docker volume.

Метаданные: UUID `id`, `ownerId`, исходное имя, content type, размер, время создания. Бинарные данные хранить отдельно от выборок метаданных, не подгружать при списках. Значение ownerId задавать из JWT.

API через Gateway:

- `POST /api/v1/files` — multipart `file`, 201, Location и метаданные; сохраняет `FileUploaded` в outbox.
- `GET /api/v1/files/{id}` — метаданные.
- `GET /api/v1/files/{id}/content` — скачивание с корректными Content-Type/Content-Disposition.

Все роли могут загружать файл. Получать его может владелец или ADMIN. Файл другого пользователя не становится публичным по знанию UUID. Ошибки: 400 для некорректного multipart/пустого файла, 401/403 по доступу, 404 при отсутствии, 413 при превышении лимита. Имя файла очищать для HTTP-заголовка, отдавать содержимое как attachment.

Лимиты согласовать на Gateway и file-service, включая накладные расходы multipart и поведение chunked-запросов. Не полагаться только на Content-Length. Подключить публичный RSA-ключ, Eureka, Config Server, Swagger, Docker build и Liquibase.

Привязка к задачам, удаление файлов, MinIO/S3, антивирус и большие потоковые загрузки в обязательный объем не входят. При требовании именно вложений к задачам потребуется отдельно определить связь и проверку проектных прав; это расширение исходного задания.

## 7. Clean Architecture

Для каждого бизнес-сервиса использовать пакеты в одном Maven-модуле, без обязательного размножения модулей на каждый слой:

```text
itmo.<service>
  domain                 # модели и правила, без Spring/JPA/Jackson
  application
    port/in              # входные сценарии
    port/out             # хранилище, каталог пользователей, outbox и прочие внешние возможности
    service              # реализация сценариев
  adapter
    in/web               # REST, API DTO, Bean Validation, mapping
    in/kafka             # consumers
    out/persistence      # JPA/R2DBC entities, Spring Data, mapping
    out/kafka            # публикация и транспортные контракты
    out/user             # Feign-адаптер в tracker-service
  configuration          # сборка зависимостей, Security, транзакции, кэш, schedulers
```

Правило зависимостей: адаптеры зависят от application/domain; application зависит от domain и собственных портов; domain не знает про адаптеры.

Конкретные изменения существующего кода:

- `TaskServiceImpl`, `ProjectServiceImpl`, `ProjectMemberServiceImpl`, `LabelServiceImpl`, `UserServiceImpl`, `AuthService`: выделить сценарии и заменить зависимости от Spring Data/Feign/Security на порты.
- `Task`, `Project`, `ProjectMember`, `Label`, `User` сейчас являются persistence-моделями. Сохранить ORM/R2DBC-аннотации и Entity-валидацию в адаптере БД, выделить независимые доменные модели и mapping. Не переносить аннотированные сущности в domain под новым именем пакета.
- Не возвращать REST DTO и `Page`/`Pageable` из независимого application-слоя. Использовать команды, результаты и простые типы пагинации; преобразовывать их на границе REST/Spring Data.
- Отделить простой `Actor` с ID/ролями от чтения Reactor/Spring Security Context. Текущий `CurrentUser` совмещает обе роли. Передачу JWT в Feign сохранить на уровне адаптеров.
- Транзакции организовать внешними декораторами сценариев/портом UnitOfWork. Обязательно сохранить атомарность создания проекта с участником, переноса задачи и добавления outbox. Проверки внешнего user-service оставить до локальной транзакции записи.
- Spring Cache, BCrypt/JWT, получение времени и UUID, scheduler и KafkaTemplate оставить во внешнем слое. Бизнес-проверки доступа должны выполняться и при прогретом кэше.
- В user-service сохранить Reactor и R2DBC без `.block()`. Reactor допустим как выбранная модель исполнения application-портов, Spring Data/Security — нет; domain остается обычной Java-моделью.
- В tracker-service сохранить WebFlux и изоляцию JPA/Feign от event loop через `BlockingOperations` либо эквивалентный внешний адаптер. Не потерять передачу Security Context и ограничения worker scheduler.

`api-gateway`, `config-server`, `discovery-server` — инфраструктурные приложения без предметной бизнес-модели. Проверить, что они содержат маршрутизацию, discovery, security/configuration; бизнес-правила туда не переносить. Пустые domain/application-слои для них не создавать. `security-common` — инфраструктурная библиотека, от нее не должны зависеть domain/application бизнес-сервисов.

ArchUnit-тестами запретить импорты Spring, JPA, Spring Data, Jackson, Feign, Kafka и адаптеров во внутренних слоях. Для application разрешить согласованный Reactor API. Тест должен также проверять зависимости между пакетами, а не только имена импортов.

| Этап | Изменения | Критерий завершения |
|---|---|---|
| 1. Clean Architecture user-service | Domain, application, R2DBC/web/security-адаптеры; архитектурные тесты | Login, BCrypt, bootstrap, роли, internal resolve, миграции и старые API сохраняются |
| 2. Clean Architecture tracker-service | Сначала задачи/проекты, затем участники/метки; порты, транзакции, Feign, кэш, worker | Старые unit/IT, JWT через реальный Feign, права, пагинация, optimistic locking и rollback проходят |
| 3. Kafka в Compose | 3 брокера, volumes, init-топики, healthchecks, настройки Config Server | describe показывает RF=3 и ISR=3; после отключения одного узла запись/чтение восстанавливаются и продолжаются |
| 4. Первый сквозной сценарий | Контракты, task outbox, notification-service, TaskAssigned | Назначение задачи → Kafka → уведомление исполнителя → чтение через Gateway |
| 5. Остальные события и надежность | Смена статуса, участники, retries/DLT, дедупликация | Нет события при rollback; дубликат не дает второго уведомления; восстановление после простоя consumer/Kafka |
| 6. file-service | Загрузка/получение, права, БД, outbox, FileUploaded | Файл загружается и скачивается побайтово; владелец видит уведомление; чужой доступ запрещен |
| 7. Общая интеграция | Все маршруты/OpenAPI, startup-скрипт, env/config, Dockerfile и Maven-модули | Полный запуск из чистого отдельного Compose-проекта без ручных операций |
| 8. Приемка и документация | Полный verify, сценарии сдачи, матрица требований, схема зависимостей | Сценарии ЛР1–4 воспроизводимы, тестовые результаты и ограничения записаны |

На этапах 4 и 6 сразу подключать новый сервис к Eureka, Config Server, Gateway, Swagger и security. Этап 7 проверяет их совместную работу. Не создавать сначала незащищенный публичный сервис.

Примеры веток/коммитов: `feature/lab4-user-clean-architecture` / `refactor(user): isolate application and persistence`, `feature/lab4-kafka-cluster` / `feat(infra): add three-node kafka cluster`, `feature/lab4-notifications` / `feat(notifications): consume task assignment events`.

## 9. Проверки и демонстрация

Существующие тесты адаптировать к новой структуре, сохранив проверяемое поведение. Для новых сценариев использовать JUnit Jupiter и Testcontainers PostgreSQL/Kafka; unit-тесты бизнес-правил не должны требовать Spring-контекст.

Обычные интеграционные тесты могут использовать один Kafka Testcontainer с тестовым RF=1. Это не доказывает трехброкерную репликацию: ее отдельно проверять на Compose-кластере.

Обязательная приемка:

1. `mvn clean verify` на JDK 21: старые и новые проверки, ArchUnit, JaCoCo не ниже 70% для бизнес-модулей и других модулей с настроенным gate; новые сервисы включить в gate без искусственного исключения бизнес-кода.
2. Проверить атомарность бизнес-записи + outbox, повторную отправку после перезапуска publisher, дедупликацию и rollback consumer. Проверить невалидное сообщение и отказ публикации в DLT.
3. Остановить notification-service: новые операции сохраняются; после запуска создаются отложенные уведомления.
4. Остановить Kafka: операции сохраняют outbox; после восстановления события доходят. Зафиксировать таймаут ожидания в smoke, не использовать бесконечное ожидание.
5. На здоровом кластере отправить событие, остановить один брокер, дождаться перевыбора и отправить следующее; проверить уведомления и ISR. После возврата брокера дождаться ISR=3. Тест с двумя выключенными узлами — дополнительный.
6. Проверить 401 без JWT, закрытый доступ к чужим уведомлениям/файлам, разрешенные операции ролей ЛР3, отсутствие паролей/токенов в событиях и ответах.
7. Загрузить файл, сравнить скачанные байты, проверить пустой/слишком большой файл, имя для Content-Disposition, сохранность после пересоздания контейнера без удаления volume.
8. Проверить через Gateway все OpenAPI-схемы и общий Swagger; максимум 50 в списке уведомлений, X-Total-Count и сохранение task feed без count.
9. Проверить Clean Architecture во всех бизнес-сервисах и отсутствие бизнес-логики в инфраструктурных приложениях.

Полные Docker-проверки выполнять в отдельном Compose-проекте с отдельными портами/volumes. Рабочие данные ЛР3 и запущенные пользовательские контейнеры не использовать как одноразовый тестовый стенд.

Итоговые материалы: обновленный README, `docs/LAB4_HANDOFF.md` с матрицей требований и фактическими результатами, краткая схема сервисов/направления зависимостей, воспроизводимые HTTP-примеры и команды проверки Kafka. Показывать отдельно тестовую проверку приложения и ручное подтверждение трехброкерной отказоустойчивости.

## 10. Что не включать без отдельной необходимости

RabbitMQ параллельно с Kafka, email/Telegram, WebSocket, MinIO/S3, Debezium, Schema Registry/Avro, пользовательская проекция вместо Feign, распределенные транзакции, Kubernetes и frontend. Эти технологии не требуются для выбранного варианта ЛР4.

## Источники технических решений

- [Apache Kafka: broker configuration](https://kafka.apache.org/37/configuration/broker-configs/) — смысл replication factor / min.insync.replicas / acks. Ссылка поясняет настройки, а не фиксирует версию образа для реализации.
- [Spring: transactional outbox strategies](https://spring.io/blog/2023/10/24/a-use-case-for-transactions-adapting-to-transactional-outbox-pattern/) — запись события вместе с изменениями БД и последующая публикация; отличия от координации отдельных транзакций Kafka и БД.
